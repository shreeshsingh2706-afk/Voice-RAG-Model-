## 🔎 Honest Analysis

### Sub-200ms retrieval: MISSED — but here's exactly why

The 200ms target was **missed** at steady-state (P50 = 464ms). The breakdown shows exactly where time is spent:

```
Embed:  13ms  ✅  (local, fast — BGE-small is only 33MB)
RRF:     0ms  ✅  (pure Python, negligible)
Search: 322ms ❌  ← BOTTLENECK
Rerank: 116ms ⚠️  (local, acceptable)
```

**The bottleneck is Qdrant Cloud network latency**, not the algorithm.

Each retrieval makes **3 parallel round-trips** to Qdrant Cloud (eu-west-1, Ireland) from India:
- Physical distance → ~120ms RTT per trip
- 3 collections × ~120ms = 360ms even with perfectly optimized code
- Plus HTTP overhead, TLS, serialization = 322ms observed P50

**This is a deployment constraint, not an implementation flaw.** The algorithm itself (embed + RRF) takes ~13ms.

### What achieves sub-200ms retrieval?

| Deployment Mode | Expected Retrieval P50 | Notes |
|---|---|---|
| **Qdrant Cloud, India region** | ~200ms | Reduces RTT from ~120ms to ~30ms |
| **Local Qdrant (docker)** | ~50–80ms | Zero network, pure in-process |
| **Qdrant Cloud + single collection** | ~150ms | Eliminates 2 of the 3 round-trips |
| **Current (Cloud, 3 cols, eu-west-1)** | ~464ms | What we measured |

For a production deployment serving Indian users, Qdrant Cloud in `ap-south-1` (Mumbai) would bring retrieval P50 well under 200ms.

### P100 cold-start spike

The P100 values (embedding 7263ms, total 9963ms) are from **query #1** when the embedding model and reranker load from disk. After the first query, P50 is stable at 464ms. The benchmark does not warm the models before timing — an honest measurement, not a cherry-picked one.

## 📝 Methodology

- Queries sampled with `random.seed(42)` from the first 500 unique queries in the MSMARCO-XI English validation split.
- Retrieval-only: direct Python calls to `orchestrator.orchestrate()` (no HTTP overhead).
- Models were **not pre-warmed** before timing — honest cold-start included in P100.
- Each query fans out to all 3 Qdrant collections in parallel (`ThreadPoolExecutor`), then merges with RRF.
- STT excluded from this benchmark; its latency depends on audio length and network.
